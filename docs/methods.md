# Analysis methods and input contracts

## Source preflight
Code: identify repository, business scope, ref, commit, local changes, shallow history and deployed version separately. Do not reset user worktrees. Database: verify database identity, schema freshness, approved joins and metric meaning before querying. A SELECT prefix or display row cap is not a complete read-only or resource guarantee. Documents: preserve original version, approval status, deployment status, attachments and truncation. Tools: distinguish a checkout from installed dependencies and a successful invocation.

## Behavior and outcomes
Define cohort, observable action and final outcome separately. Generated records are not clicks. State time zone, object grain, deduplication and outcome window. Use mutually exclusive result groups where appropriate. Failed or missing batches are not zero values.

## Growth and causal effects
Use comparable windows and decompose users, orders and amounts; partial periods and immature outcomes need explicit treatment. Observational differences do not establish intervention effects. Define pre-intervention cohorts, controls, selection bias and alternative explanations before estimating impact.

## Disputes and cross-system diagnosis
Trace requested, confirmed, executed and observed states. Match identities and versions without exposing personal information. Distinguish code behavior from the incident deployment. Keep plausible explanations separate from confirmed facts.

## Coverage and technical support
A fix commit is engineering evidence, not an incident count. An API or retry loop does not prove deployed service coverage. Check authorization, operational instructions, exhausted retries, time windows, escalation ownership and actual user recovery. Separate inventory unfreezing from physical device unlocking.

## Requirements and scope changes
Keep current evidence separate from future product decisions. Scope by product, country, role, client and deployment. Shared branding does not prove shared backend behavior. For cross-brand funnels, separate platform-new users from existing customers and validate account reuse before claiming incremental conversion.

## Risk strategy
Separate input semantics, decision-time availability, rule contribution and observed outcomes. Reject leakage from future outcomes. Do not infer causal variable importance from rule presence. Proposed policies require explicit parameters, shadow validation and authorization before production use.

## Learning
Keep generic protocols, scoped methods, host business knowledge and case evidence distinct. Reuse or narrow an existing method before adding one. Record validation scope and counterexamples. No automatic promotion of unverified business facts.

These are English portable method summaries. Historical host-specific examples and Chinese source documents remain private; they are not shipped as authoritative business rules.
